# 下一步修改建议

日期：2026-11-09。以下基于本次整合后的代码，不要求重写现有业务或替换数据库。

## 第一优先：长任务可以离开页面后继续

目前问答和研究依赖当前连接，刷新、切换页面或服务重启后无法接着运行。建议把“创建任务”和“订阅进度”拆开：任务先持久保存，再由后台执行；前端只负责订阅，断线后按最后收到的事件继续读取。

先增加任务状态、事件顺序和明确的取消接口，再接入后台工作进程。研究与实验核验使用共同的任务标识和失败状态，保留不同的处理流程。验收应覆盖重复提交、断线重连、重启恢复和取消传播；不得把已失败的任务当作完成。

## 第二优先：把核验用量计入统一用量页

研究已记录模型请求、搜索及 token 用量；实验核验目前保存内容和检查结果，没有把整理两份资料产生的模型用量纳入同一统计。建议模型适配器返回内容和 usage，由应用服务保存每次调用记录，再由现有用量接口汇总。

失败和取消前已经返回的用量也应保留，不把缺失 usage 当作零，不混入旧消息重复计算。应用费用估算与服务商账单分开展示。此次移除研究配额后，优先提供透明的使用记录和消耗提示，不重新引入隐式次数上限。

## 第三优先：更容易找到论文里的正确实验

目前按文本片段整理信息，人工仍需检查模型是否选中了正确实验行。建议先在上传解析时记录可靠的页码、章节和表格上下文；核验页允许明确选择目标模型、表号和实验设置，再执行比较。

先支持文本 PDF 的可靠页码和表格预览，再评估 OCR。无法确认坐标时继续显示原文片段，避免给出看似精确但错误的位置。验收至少包含多张同名模型表格、跨页表格、预训练来源差异和 OCR 失败。

## 第四优先：提高核验质量并保留评估依据

保留现有确定性规则测试，增加经人工检查的论文和真实运行摘要。将抽取是否正确、原文是否支持、比较判断是否正确分开统计，重点观察“实际不一致却被判为一致”的情况。

历史 20 组评估采用合成运行摘要，不能代表真实训练复现；旧九项与新增训练条件后的结果也不能直接混算。后续每次评估固定代码版本、模型、提示、样本和人工答案，同时记录耗时、usage 与失败原因。真实模型评估需单独获得调用授权。

## 第五优先：历史和资料更适合长期使用

统一历史目前一次读取所有记录，资料选择与核验列表也缺少分页。建议先在后端增加游标分页、任务类型筛选和标题搜索，再接前端滚动加载；保持现有记录链接可直接打开。

随后增加研究项目或资料分组，把同一论文的问答、实验核验和不同运行摘要关联起来。删除前明确影响范围；如增加回收站，应给出保留期限和恢复操作。不要只靠前端过滤掩盖后端全表读取。

## 配套维护

- 为新建任务、原文查看、修改检查结果和确认保存增加少量稳定的浏览器回归；继续使用模拟模型，避免日常测试产生费用。
- 保持 API 的兼容入口有明确淘汰计划：先确认旧客户端已迁移，再删除 `/api/comparisons` 和旧页面跳转。
- 给迁移增加真实 PostgreSQL 测试，覆盖旧核验补历史、确认记录保留、外键和并发删除。不要在业务数据库执行迁移测试。
- 日志关联任务 ID 和请求 ID，记录耗时与错误类型，避免写入密钥、用户全文和模型私密思考。

建议按“任务恢复 → 用量完整性 → 原文定位 → 评估质量 → 历史与项目管理”的顺序推进。每项独立交付，保留现有问答、研究和人工核验能力。
